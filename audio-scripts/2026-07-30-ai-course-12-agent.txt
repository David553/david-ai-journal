第12课：让模型"动起手来" —— Agent 的循环、工具、记忆与评测

本课目标

前 11 课我们一直在回答一个问题：模型如何生成好的文本（或图像）。但你日常用的 Claude Code、各类"自动帮你订机票/写周报"的产品，都不只是"生成文本"——它们会执行命令、读文件、根据结果调整下一步。本课是路线 A 部分的最后一块拼图：如何把一个只会预测下一个 token 的模型，包装成一个能在环境里持续做事的系统（Agent）。学完你能解释：Agent 的骨架代码长什么样；为什么 Agent 跑长任务容易"越跑越偏"；以及为什么评测一个 Agent 比评测一个模型难得多、贵得多。

今日论文

OmegaUse-OfficeVal（arXiv:2607.27155）：一个评测 LLM Agent 完成长程办公任务的 benchmark，特色是给每个任务标注了"人类完成需要多少小时、市场价大约多少钱"，把评测从"能不能做对"升级为"做这件事在经济上划不划算"。

背景铺垫

*1. Agent = LLM + 工具 + 循环*

先破除一个迷思：LLM 从来没有"真正调用"过任何工具。所谓工具调用（tool calling / function calling），是系统在 prompt 里放一份工具说明书（schema）——工具名、参数、用途描述——然后模型在合适的时机生成一段结构化文本（通常是 JSON），比如 {"tool": "search", "query": "上海天气"}。外部程序解析这段文本、真正去执行、再把结果喂回给模型。模型只是被训练成"在该用工具时生成这种格式的 token"——这是第 9 课 SFT 的直接延伸：工具调用能力就是用大量带工具调用的对话数据微调出来的。

类比：LLM 是一个只能通过电话下达指令的军师，Agent 框架给他配了手和脚。军师说"去侦察东门"，士兵去执行，回来报告"东门有伏兵"，军师再决定下一步。

几个关键术语：工具执行的外部世界叫环境（environment）；执行结果叫观察（observation）；从任务开始到结束的完整序列（行动₀, 观察₀, 行动₁, 观察₁, …）叫一条轨迹（trajectory）。这个"行动前先写一段思考、再看观察决定下一步"的模式叫 ReAct（Reason + Act）。

注意一个深刻的事实：Agent 的"状态"就是那个不断变长的 history。它本质上还是第 2 课的自回归生成——只不过序列里混入了环境的反馈。所以你学过的东西全部直接适用：上下文窗口（第 5 课）决定 Agent 最多能"记住"多长的工作过程；KV Cache（第 1 课）决定每一步推理要占多少显存——Agent 跑得越久，上下文越长，推理越贵越慢。

*3. 记忆：窗口之内与窗口之外*

上下文窗口就是 Agent 的短期记忆，但它有限且昂贵。于是有两个补救：上下文压缩（把早期历史摘要成几句话，腾出窗口）和长期记忆（把重要信息写到外部存储，需要时用第 3 课的 embedding 相似度检索捞回来）。这就是"个性化 Agent 记得你偏好"的实现原理：不是模型记住了你，而是系统检索到了关于你的笔记。

*4. 长程任务与误差累积——Agent 最硬的数学*

规划（planning）指把大任务拆成子步骤。难点不在拆，而在一个残酷的乘法：假设 Agent 单步做对的概率是 p，一个需要 n 步、且一步错全盘错的任务，端到端成功率是 pⁿ。p = 0.99 听起来很强，但 n = 200 时 0.99²⁰⁰ ≈ 13%。这就是长程（long-horizon）任务难的本质：误差指数级累积。所有让 Agent 变实用的工程手段——每步后验证结果、失败重试、设检查点、让错误可恢复——本质上都是在把"一步错全盘错"改造成"错了能改"，打破这个指数。

*5. Agent 评测为什么难*

评测模型（如问答准确率）是"固定输入 → 比对输出"。评测 Agent 则要：搭一个可复现的环境（真实的 Excel、浏览器）、让 Agent 跑完整条轨迹、再判断环境的终态是否满足要求——同一任务可能有无数条正确路径，没法逐 token 比对。而且成功率只是一半：Agent 每一步都在烧 token（钱）和时间，一个花 50 美元完成 10 美元人工任务的 Agent，准确率再高也没有商业意义。

回到论文

现在 OmegaUse-OfficeVal 的设计就很好懂了。它收集了 100 个来自真实从业者的办公套件任务（做表格、写文档之类），平均每个需要人类 2.32 小时——按刚才的数学，这是典型的长程任务，步数多、误差累积严重，专门打在当前 Agent 的软肋上。它的核心创新是给每个任务配了两个经济信号：人力耗时和任务价格代理。这样评测输出的不只是"成功率 X%"，而是能直接回答"让 Agent 做这件事，花的推理成本（≈ 轨迹总 token 数 × 单价）是否低于雇人的钱"。这把 Agent 评测从实验室指标拉到了经济可行性判断——也解释了为什么工业界如此在意推理成本优化（这正是我们 B 部分要学的全部内容的动机）。
