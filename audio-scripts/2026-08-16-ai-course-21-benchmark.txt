第21课：分数是怎么来的 —— 评测的质量、污染、判分偏置与系统 benchmark

本课目标

到上一课为止，你已经走完了整条链路：模型怎么建模、怎么训练、怎么解码、怎么对齐（第1–11课），怎么做 Agent（第12课），以及从 GPU 到分布式再到线上容量的整套 infra（第13–20课）。但有一件事贯穿全程却一直没讲清楚：我们凭什么说 A 模型比 B 模型好、这次优化有没有效？

这就是评测（evaluation）。它是知识图谱的"收口"：训练靠它选 checkpoint，对齐靠它判断是否变笨，量化和投机解码靠它证明"无损"，serving 靠它把吞吐和质量绑在一起报数。学完这课，你能解释这些困惑：为什么同一个模型在不同榜单上 MMLU 差 5 分？为什么"提升 1.2 个点"可能纯属噪声？为什么榜单第一的模型你用起来却很一般？

今日经典案例

今天没有合适的新论文，用一个经典系统打底：HELM（Holistic Evaluation of Language Models，Stanford 2022）。它的核心主张是"评测不是一个数字，而是一个矩阵"——场景 × 指标全展开，把准确率、鲁棒性、校准、偏见、效率并列报告。后半段再用 MLPerf Inference 作为系统 benchmark 的对照。

背景铺垫

1. 一次评测 = 数据集 + 指标 + 协议

新手最容易漏掉第三项。同一个数据集、同一个指标，只要协议（prompt 模板、few-shot 示例数量与顺序、解码策略、答案抽取规则）不同，分数就能差好几个点。

以 MMLU 这类四选一题为例，至少有两种主流判分方式：

（a）logprob 打分。 不让模型生成，而是把四个选项分别拼到题干后面，比较对数概率（第2课的 logits/softmax 直接派上用场）：

问题来了：选项文本长短不一，长选项天然概率低（每多一个 token 就多乘一个小于 1 的数）。于是有了长度归一化 logprob / n_tokens，或者按选项的无条件概率归一化 logP(opt|q) - logP(opt)。三种归一化，三个分数，都合法。

（b）生成式打分。 直接让模型输出 "A"/"B"/"C"/"D"，再正则抽取。这时模型的指令遵循能力（第9课 SFT）被算进了分数里，而且模型答 "The answer is (B)." 时，抽取规则写得糙一点就判错。

结论：跨来源的分数不可直接比较。这也是 lm-evaluation-harness 这类工具的价值——不是它更聪明，而是它把协议固定下来了。

2. 生成任务怎么判分：从 exact match 到 pass@k

自由生成没有标准答案。三条路：

- 规则匹配：exact match、F1（问答）、BLEU/ROUGE（翻译摘要）。便宜、稳定，但对同义表达毫无办法。
- 可执行验证：代码评测最幸运——跑单测就行。指标是 pass@k：采样 n 个答案，其中 c 个通过，无偏估计为

  $$\text{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$$

  直觉：从 n 个里随机抽 k 个，一个都不对的概率是多少，用 1 减掉。注意 pass@1 和 pass@100 衡量的是不同东西——前者是"一次答对"，后者是"能不能答对"，对应第8课的解码温度选择完全不同。
- 模型判分（LLM-as-a-judge）：让强模型给答案打分或做两两比较。它是目前开放任务的事实标准，但有系统性偏置，见第 4 点。

3. 你的"提升"可能是噪声

这是最被忽视、也最容易自查的一点。假设测试集 n=1000 题，准确率 p=0.70，把每题看作独立伯努利试验，标准误：

$$SE = \sqrt{\frac{p(1-p)}{n}} = \sqrt{\frac{0.7\times0.3}{1000}} \approx 1.45\%$$

95% 置信区间约 ±2.8 个百分点。也就是说，在 1000 题的子集上"70.2 → 71.5"这种提升，统计上和没提升区分不开。 更糟的是，很多榜单还在多个子集上取平均、只跑一次采样、temperature 还不为 0。

自查清单：报分数时给出 n 和置信区间；比较两个模型时用配对检验（同一批题，看 A 对 B 错 / A 错 B 对 的数量差，即 McNemar 检验），比独立比较敏感得多。

4. 判分偏置与 Goodhart 定律

LLM 判分的已知偏置：位置偏置（同样两个答案，交换先后顺序，判决会翻转，所以必须做双向平均）、长度偏置（长答案得分更高）、自我偏好（模型偏爱自己家族的输出风格）、格式偏置（带 markdown 列表的更"专业"）。

人类偏好评测同样有坑。Chatbot Arena 用两两对战 + Bradley-Terry 拟合出 Elo 分——你在第9课学奖励模型时已经见过这个模型，只是那时用来训练，这里用来排名。它的问题是：投票人分布不代表你的业务，且同样吃长度和排版的红利。

Goodhart 定律："当一个指标变成目标，它就不再是好指标。" 榜单一旦公开，就会被反复在验证集上做选择（选 checkpoint、调 prompt、挑数据配比），这叫 test set overfitting——即使从未直接训练在测试集上，反复用它做决策也会让分数虚高。

5. 数据污染（contamination）

最严重的一类失效：测试题出现在预训练语料里，模型是在背答案。检测手段：

- n-gram 重叠：拿测试题在训练语料里查 13-gram 命中（GPT-3/Llama 论文的做法）；
- canary string：数据集里嵌入一个唯一随机串，如果模型能续写出来，说明它见过；
- 时间切分：只用模型知识截止日之后产生的题目（LiveCodeBench、LiveBench 的思路），这是目前最干净的做法；
- 私有/动态测试集：题目不公开，或每期换新。

一个便宜的启发式检查：把选择题的正确选项换成"以上都不对"，或者打乱选项顺序，如果分数暴跌，很可能是记忆而非推理。

6. 系统 benchmark：质量不锁死，吞吐数字没意义

前面讲的是"模型多好"，infra 侧要回答的是"多快多便宜"。这里的核心纪律只有一条：任何吞吐/延迟数字，必须在质量等价的前提下比较。

因为你在第18课学的量化、蒸馏、投机解码，前两个都会掉质量。声称"吞吐提升 3 倍"却不报 INT4 之后 MMLU 掉了多少，就是耍流氓（投机解码是个例外——它理论上分布无损，这正是它的卖点）。

MLPerf Inference 的做法值得学：固定模型和精度、规定准确率不得低于 FP32 基线的 99%（或 99.9%），然后在两个场景下报数——Offline（纯吞吐）和 Server（泊松到达 + P99 延迟约束）。后者就是第20课的 goodput：在 SLO 约束下能扛住的 QPS，而不是把 batch 拉满得到的虚高吞吐。

同理，你自己压测时至少要记录：输入/输出长度分布（决定 prefill:decode 比例）、并发数、TTFT/TPOT 的 P50 和 P99、精度设置。少任何一项，别人都复现不了。

回到 HELM

现在再看 HELM 的设计，每一条都是在对抗上面的失效模式：

1. 场景 × 指标矩阵：不报单一均值，而是 16 个场景 × 7 类指标全展开。因为"平均分"会掩盖第1点说的协议差异和能力短板——一个模型可能靠几个高分子集把均值撑起来。
2. 7 类指标并列：accuracy、calibration（第11课学过：模型说 80% 把握时是否真有 80% 正确率）、robustness（对拼写错误、同义改写等扰动的稳定性）、fairness、bias、toxicity、efficiency（推理成本）。这正是"可靠性"与"质量"的分离——一个准确率 85% 但校准极差的模型，在需要 defer（选择性回答）的生产场景里可能不如准确率 80% 但校准良好的模型。
3. 协议标准化：所有模型跑同一套 prompt 模板、同样的 few-shot 数量、同样的解码配置，且全部原始输出可查。这直接对应第1点——只有协议对齐，横向比较才成立。
4. 明确报告不确定性和成本：把 efficiency 放进指标矩阵，等于承认"质量-成本"是一个 trade-off 曲面，而不是一个排名。

HELM 的局限也清楚：它诞生于 2022 年，以补全式任务为主，对今天的推理模型、Agent（第12课的终态判定式评测）覆盖不足；而且公开榜单本身逃不掉第4、5点的污染与 Goodhart 压力。但它确立的心智——评测是多维报告而非单一排名——至今没有过时。
