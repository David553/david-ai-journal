第23课：文字是怎么变成 token 的 —— 分词器、BPE 与词表设计

本课目标

前 22 课里，"token"一直是被默认给定的原子单位：第 1 课讲它进 KV Cache，第 2 课讲在词表上算 softmax，第 3 课讲它查 embedding 表。但谁决定了一段文字被切成哪些 token，我们从没讲过。这是整条流水线的最前端——在 embedding 查表之前的那一步。

按路线图，这是 A1「Token、概率建模与自回归生成」里唯一没补的洞。补完它，你能解释一批看似玄学的现象：为什么模型数不清 "strawberry" 里有几个 r；为什么同样一句话，中文比英文贵两三倍；为什么词表从 32k 扩到 128k 是 Llama 3 的重要改动；为什么两个模型 tokenizer 不同就没法做投机解码。

今日案例

今天没有合适的新论文。用经典案例：GPT-2 的 byte-level BPE（Radford et al., 2019）——它确立了此后几乎所有主流 LLM 的分词范式，并对照 Llama 3 把词表扩到 128k 的取舍。

背景铺垫

一、三种朴素切法，两条死路

要把字符串喂给模型，必须先切成有限词表里的离散单元。最直觉的两种都不行：

按字符切（vocab ≈ 几百）：词表极小、永不出错，但序列长度暴涨。"international" 一个语义单元变成 13 个 token。回忆第 7 课的 C≈6ND 和第 5 课的注意力 O(L²)——序列长 4 倍，训练成本至少 4 倍，注意力项 16 倍，KV Cache 也 4 倍。而且单个字符几乎不携带语义，模型要花很多层去重新拼词。

按词切（vocab ≈ 几十万）：序列最短，但词表爆炸（第 3 课讲过 embedding 矩阵是 V×d 的查表，V 大则显存和输出层计算都吃紧），而且必然遇到 OOV（未登录词）——训练时没见过的新词、拼写错误、代码里的变量名，全部退化成 <unk>，信息直接丢失。中文更尴尬：没有空格，"按词切"本身就需要一个分词器。

子词（subword） 是折中：高频词整个作为一个 token，低频词拆成若干常见片段。"internationalization" → international + ization。既控制了词表，又保留了组合能力，还天然没有 OOV。

二、BPE：一个压缩算法被拿来当分词器

BPE（Byte Pair Encoding）原本是 1994 年的数据压缩算法，思路简单到一句话：反复找出语料里最高频的相邻符号对，把它合并成一个新符号。

三、byte-level：GPT-2 的关键一招

朴素 BPE 的基础单元是"字符"，那 Unicode 有十几万个字符，光基础词表就撑不住；漏掉的字符还是会变成 <unk>。

GPT-2 的做法：把基础单元从字符换成字节。任何文本 UTF-8 编码后都是字节流，基础词表固定 256 个，然后在字节序列上跑 BPE。这样：

- 永远不会 OOV——任何输入，最差退化成逐字节，也能表示（这叫 byte fallback）。
- 一个中文字符是 3 个 UTF-8 字节。如果训练语料里中文少，BPE 就学不到把这些字节合并成词的规则，中文只好逐字节切——这正是早期 GPT 模型中文 token 消耗惊人的技术原因。

另一个细节是 pre-tokenization（预切分）：GPT-2 先用一条正则把文本切成"词块"（空格+单词、数字、标点各成一块），BPE 只在块内合并，禁止跨块。否则模型会学出 "World."、"World!" 这种把标点粘进词里的 token，浪费词表。这也解释了一个高频坑：GPT 系 tokenizer 里前导空格属于词，" hello" 和 "hello" 是两个不同 token。你的 prompt 如果以空格结尾，模型看到的分布会明显偏移——写 few-shot 模板时别在末尾留空格。

（同期另一路是 SentencePiece + unigram LM：不做贪心合并，而是先建大候选集，再用概率模型迭代删掉对似然贡献最小的子词。它把空格显式编码成 ▁，对无空格语言更友好。思路不同，工程效果接近。）

四、词表多大合适：一笔可以算的账

设词表 V、隐层维度 d。变大的代价：

- embedding 表 + 输出层 lm_head 各 V×d 参数（第 3 课的 weight tying 可以省掉一份）。V=128k、d=4096 时，单份就是 5.2 亿参数——对 7B 模型是不可忽略的一块。
- 每生成一个 token，输出层要做一次 V×d 的矩阵乘（约 2Vd FLOPs），再在 V 上做 softmax。decode 阶段本来就是 memory-bound（第 13 课），这一层的权重读取是实打实的开销。
- 长尾 token 见得少，embedding 训练不充分。

变大的收益：压缩率提升。用 fertility（平均每个词耗多少 token）衡量，V 越大 fertility 越低，同样的文本序列长度 L 越短。而 L 变短是全链路的收益：训练 token 数 D 变小（C≈6ND 直接省算力）、注意力 L² 项变小、KV Cache 变小、同样的上下文窗口能装更多真实内容、按 token 计费的成本下降。

所以存在一个最优 V。Llama 2 用 32k，Llama 3 扩到 128k，官方说法是英文 fertility 降约 15%——省下的序列长度成本，压过了多出来的输出层开销。趋势是：模型越大、训练数据越多、多语言要求越高，最优 V 越大。

五、几个必须知道的坑

- 数字：如果 tokenizer 把 1234 切成 123|4、把 1235 切成 1|235，模型学算术就像在读一门切分不一致的语言。现代模型普遍强制数字按固定分组（逐位或三位一组）切，算术能力立刻改善。
- 字符级任务：strawberry 可能是 3 个 token，模型的输入里根本不存在"字母"这个层级。数 r 的个数对它是隔着一层抽象的推理题——这是表示问题，不是智力问题。
- 多语言不公平：同一段语义，中文/泰文/印地语的 token 数常是英文的 2–4 倍。这意味着更贵的 API 账单、更小的有效上下文、更差的长文本表现。
- glitch token：训练 tokenizer 的语料和训练模型的语料不同时，某些 token（著名的 SolidGoldMagikarp）在模型训练中几乎没出现过，它的 embedding 基本是随机初始化的噪声，输入后模型行为异常。
- 跨模型对齐失败：第 18 课的投机解码要求 draft 与 target 共享词表，第 18 课的蒸馏要在同一词表上算 KL——tokenizer 不同，这些技术全部失效。第 21 课的 logprob 打分同理，切分方式变了，序列概率就没有可比性。

回到案例

现在可以完整复述 GPT-2 的设计了：用 256 个字节作基础词表保证零 OOV → 用正则预切分防止标点/空格污染词表 → 在字节序列上跑 BPE 合并出 50257 个 token，对英文取得好压缩率。它一次性解决了 OOV、多语言可表示性、词表规模三个问题，代价是非英语语种的压缩率被牺牲。此后的演进（Llama 3 扩到 128k、数字强制分组、多语言语料重新训 tokenizer）本质都是在同一框架内重新调这笔账。

也有人想绕开整件事：直接在字节上建模、动态学习切分边界的 tokenizer-free 路线（如 Byte Latent Transformer 一类工作）已有雏形，但还没在大规模上取代 BPE。
