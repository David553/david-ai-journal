第17课：一台 GPU 同时服务上百个请求 —— 从静态批处理到 Continuous Batching 与 PagedAttention

本课目标

前面我们把"单个请求"的推理拆透了：第1课讲了 prefill/decode 两阶段和 KV Cache，第13课讲了 decode 是 memory-bound、batching 能提升算术强度，第16课把 KV Cache 的显存账算清楚了。但线上不是一次跑一个请求——是几百个用户同时发来长短不一的请求，你只有一块（或几块）GPU。本课要回答：serving 系统靠什么把一块 GPU 的吞吐榨到极限？学完你能解释三件事：为什么"凑一批一起算"这种朴素做法浪费严重、continuous batching 到底改了什么、以及为什么 KV Cache 的显存管理才是吞吐的真正天花板。

今日经典案例

今天没有合适的新论文，用两个奠基性系统当案例：Orca（OSDI 2022，提出 continuous batching）和 vLLM 的 PagedAttention（SOSP 2023，几乎是今天所有推理引擎的标配）。

背景铺垫

1. 先回顾"为什么要 batch"。 第13课说过：decode 阶段每步只生成 1 个 token，却要把整个模型权重从 HBM 搬进来算一遍，算术强度极低，GPU 算力空转。把 B 个请求的 decode 拼成一个 batch，一次权重搬运服务 B 个请求，算术强度涨 B 倍——这就是 batching 提升吞吐的本质。

2. 朴素做法：静态批处理（static batching）的两个坑。
- 凑批延迟：要等够 B 个请求才开算，先到的请求干等着 → 首字延迟（TTFT）变差。
- 队头阻塞（head-of-line blocking）：一个 batch 必须等所有序列都生成完才释放。假设 batch 里有个请求只输出 10 个 token，另一个要输出 500 个——前者早就完事了，它的槽位却被锁在 batch 里空转到第 500 步。GPU 大量算力浪费在"已完成但没释放"的空槽上。

3. Continuous batching：调度粒度从"请求"降到"迭代"。

Orca 的关键洞察：不要以请求为单位组批，以 token 迭代为单位组批。每生成一个 token（一次前向），就重新组织一次 batch：
- 哪个序列吐出了 EOS，立刻把它踢出、释放槽位；
- 等待队列里的新请求马上补进这个槽位。

于是 batch 的成员每一步都在变，GPU 永远是满载的，没有空槽空转，也不用等长序列。这一个改动通常就能把吞吐拉高好几倍。代价是调度变复杂：同一 batch 里可能有的序列在 prefill、有的在 decode，kernel 要能混着处理。

4. 真正的瓶颈：KV Cache 的显存碎片。

Continuous batching 想塞更多请求进 batch，但塞得下多少，取决于显存能装多少 KV Cache。第16课算过，KV Cache 大小 ∝ 层数 × 头数 × head_dim × 序列长度 × batch。麻烦在于序列长度事先不知道——模型生成到 EOS 才停。

朴素系统怎么办？给每个请求预留一块连续的、按 max_seq_len 大小的显存（比如 2048 个 token 的位置）。问题致命：
- 内部碎片：请求实际只生成了 100 个 token，剩下 1948 个位置的显存白占着不能用。
- 外部碎片：请求长短不一，连续分配后显存被切成东一块西一块，剩的零头装不下新请求。

结果：明明显存够，却因为要"连续 + 按最大预留"而装不下几个请求，batch size 上不去，吞吐被卡死。vLLM 论文实测，这种浪费能吃掉 60%~80% 的 KV Cache 显存。

5. PagedAttention：把操作系统的虚拟内存搬进来。

作为工程师你熟悉这个套路——操作系统从不要求进程的内存物理连续，它用"分页 + 页表"：进程看到的是连续的逻辑地址，背后是散落各处的物理页，页表负责映射。vLLM 照搬：

- 把每个序列的 KV Cache 切成固定大小的块（block/page），比如每块存 16 个 token 的 K、V。
- 维护一张块表（block table），把序列的"逻辑块"映射到显存里任意位置的"物理块"。
- 按需分配：序列每多生成 16 个 token，才申请一个新物理块，从空闲块池里随便挑一个。

这样一来，物理块不必连续，外部碎片几乎为零；每个序列最多浪费"最后一个没填满的块"（< 16 个 token），内部碎片被限制在 1 个块以内。显存利用率逼近 100%，能同时容纳的序列数暴涨。代价是 attention kernel 要改造：算注意力时，得按块表把散落的 K/V 块"聚"起来再算。

额外红利是共享：并行采样（一个 prompt 采 n 个候选）或多个请求共用同一段系统提示词时，这些序列可以共享同一批物理块，只在要写入不同内容时才复制（写时复制 copy-on-write）——这就是"前缀缓存"的底座。

6. 显存满了怎么办：抢占与交换。 当一个正在跑的序列要申请新块、显存却满了，调度器会抢占（preempt）某些序列——把它们的 KV 块换出到 CPU 内存（swap），或干脆丢掉、以后重新 prefill 算回来，腾出空间给高优先级请求。

回到案例

把链条串起来：vLLM = Orca 的 continuous batching + PagedAttention 显存管理器。逻辑闭环是——decode 是 memory-bound（13课），所以吞吐取决于能并发多少序列；能并发多少，取决于 KV Cache 显存装得下多少（16课）；而装得下多少，被"连续 + 预留"的碎片问题卡死。PagedAttention 用分页拆掉这个天花板 → 并发序列数大增 → continuous batching 有足够多请求把 GPU 一直喂满 → 吞吐相对旧系统提升 2~4 倍，且不牺牲延迟。

顺带记住几个 serving 的核心指标：吞吐（tokens/s）、TTFT（首字延迟，prefill 决定）、TPOT / 每 token 间隔（decode 决定）、goodput（满足延迟 SLA 前提下的有效吞吐）。它们之间要权衡：batch 越大吞吐越高，但单请求的 TPOT 会变差。
