第19课：把一次问答拆到一群卡上 —— 分布式推理：并行策略、通信与 PD 分离

本课目标

第15课讲了分布式训练（DP/TP/PP），第16~18课讲了单卡视角的推理生命周期、serving 与加速。今天把两条线交叉：当一个模型太大、或流量太高，一张卡撑不住线上服务时，并行策略要怎么选？学完你能回答三个实际问题：为什么线上部署 70B 模型几乎都用"机内 TP=8"，而很少让 TP 跨机器？为什么 decode 阶段加卡不一定变快？为什么 Kimi、DeepSeek 这类大厂都把 prefill 和 decode 拆到两群不同的机器上？

今日论文/经典案例

今天的论文里没有正中"分布式推理"主题的（[29] HiSparse 解决的是同一个"KV Cache 装不下 HBM"的问题，但走的是单机 CPU-GPU 分层路线，课末会顺带呼应）。所以本课用两个经典系统做案例：DistServe（OSDI'24）和月之暗面的 Mooncake——它们共同定义了当前主流的 PD 分离架构。

背景铺垫

1. 同一套刀法，切的东西不同。 训练并行只追一个指标：吞吐。梯度同步每次迭代才发生一次，消息是 GB 级的大块数据，还能与计算重叠。推理则同时背着两个 SLO——TTFT 和 TPOT（第17课）——而且通信模式完全变了：TP 推理时，每生成一个 token，每一层都要做两次 all-reduce（attention 输出后一次、MLP 输出后一次，对应第15课 Megatron 的行并行收尾）。一个 80 层的模型，每个 token 要通信 160 次。通信从"每次迭代一次大件"变成"每个 token 几百次小件"，这彻底改变了瓶颈的性质。

α 是延迟项——不管发多少数据都要付的固定开销（发起通信的 kernel、同步、协议栈），机内 NVLink 约 3~5µs，跨机网络约 20~30µs；β 是带宽，n 是数据量。训练的消息大（GB 级），n/β 主导，所以第15课说训练是 bandwidth-bound。而 decode 的 all-reduce 消息小得可怜：数据量 ≈ batch × hidden × 2 字节，batch=8、hidden=8192 时只有 128KB，在 NVLink 上传输不到 1µs——远小于 α。也就是说，decode 的通信是 latency-bound 的：带宽翻倍几乎不提速，唯一有效的是降低 α 和减少通信次数。算一笔账：80 层 × 2 次 × α。机内 α=5µs 时，每 token 通信地板是 0.8ms，占 TPOT=20ms 的 4%，可以接受；跨机 α=30µs 时变成 4.8ms，占 24%——这就是"TP 不出机"这条铁律的全部由来。

3. 推理视角重新给并行排序。
- TP 是唯一能降低单 token 延迟的并行：decode 是 memory-bound（第13课），瓶颈是把权重从 HBM 搬进计算单元，TP=8 让 8 张卡各搬 1/8，单步时间近似除以 8。代价就是上面那 160 次 all-reduce，所以只在 NVLink 域内做。
- PP 不降延迟（token 还是要顺序流过所有层），但能装下更大的模型、提高吞吐；它只在层间切点传一次激活，通信次数少，适合跨机。
- DP 呢？推理没有梯度、没有优化器状态（第16课的显存账只剩参数+KV+激活），梯度同步整个消失——DP 在推理里退化成多副本 + 负载均衡：完全不通信，天然的扩容和容错手段。

4. PD 干扰与 PD 分离。 prefill 是 compute-bound 大矩阵乘，decode 是 memory-bound 小步快跑（第13、17课）。continuous batching 把两者混进同一个 batch：一个 4K prompt 的 prefill 会独占 GPU 几百毫秒，同批的 decode 用户立刻看到 TPOT 尖刺——这叫 prefill-decode 干扰。缓解办法一是 chunked prefill：把长 prefill 切成小块，与 decode 混合调度，摊平尖刺。办法二更彻底：PD 分离——prefill 用一群机器（大 TP，压 TTFT），decode 用另一群机器（大 batch，压吞吐），prefill 算完把 KV Cache 通过网络传给 decode 机。代价是 KV 传输，但账算得过来：8B 级模型（GQA，8 个 KV 头×128 维×36 层）一个 4K prompt 的 KV 约 600MB，走 400Gbps 网络约 12ms——相比 prefill 本身的几百毫秒，九牛一毛。换来的是两个阶段各自独立选并行策略、独立扩缩容。

5. 容错：推理的"状态"很轻。 训练挂一张卡，全局停摆等 checkpoint 恢复；推理的状态只有请求本身和 KV Cache——某张卡挂了，把它上面的请求路由到别的副本重新跑一遍（请求级重试），用户只感到一次变慢的响应。再配上缓存感知路由：相同 system prompt 前缀的请求尽量发到已缓存该前缀 KV 的实例（第17课的前缀共享），命中就免掉重复 prefill。

回到案例

DistServe 的核心论证用的正是你已学的 goodput（第17课）：混部时，为了同时满足 TTFT 和 TPOT 两个 SLO，只能压低 batch、牺牲利用率；拆开后 prefill 池用激进的大 TP 压 TTFT，decode 池用适度 TP + 超大 batch 拉吞吐，每张 GPU 的 goodput 提升数倍——即使付了 KV 传输的钱。Mooncake 更进一步，把架构定义为 "KV-cache-centric"：prefill 池、decode 池之外，还有一个横跨各机 CPU 内存和 SSD 的分布式 KV 缓存池，前缀命中就直接取现成 KV。这和今天 [29] HiSparse 是同一个世界观：KV Cache 不必住在 HBM 里，它是一种可以分层、可以搬运、可以共享的资产。
