## 第14课：给数字"减肥" —— 数值精度（FP32/BF16/FP8）、张量布局与 kernel

**本课目标**

第13课的 roofline 告诉我们：decode 是 memory-bound，每个字节的搬运都金贵。本课往下钻一层，看三个更微观的问题：张量里的每个数**到底占几个字节、长什么样**；这些数**在显存里怎么排列**；GPU 上的一次计算（kernel）**如何搬运它们**。学完你能解释：为什么现代训练用 BF16 而不是 FP16；为什么把权重字节数减半、推理几乎就能快一倍；量化伤精度到底伤在哪；以及工程师说"写个 fused kernel"时是在优化什么。这是 B 段 infra 路线的第二块基石，后面的分布式训练、量化推理全部建在它上面。

**今日论文**

MixFrag（arXiv 2607.28589）：ViT 的混合精度后训练量化——先测出模型各组件对低精度的"脆弱度"，再像分预算一样给不同组件分配不同位宽。它是"精度是一种稀缺资源"这个观点的完美案例。

**背景铺垫**

**1. 浮点数就是二进制科学计数法。** 一个浮点数存三段：符号位、指数位、尾数位，值 ≈ 符号 × 1.尾数 × 2^指数。FP32 是 1+8+23 共 32 位。两类位各管一件事：**指数位决定动态范围**（能表示多大和多小的数，好比仪器的量程），**尾数位决定精度**（相邻两个可表示数之间的间隙，好比刻度密度）。关键直觉：浮点的刻度**不是均匀的**——数越大，相邻刻度的绝对间隙越大，但相对误差恒定。这和整数的均匀刻度形成本质区别，后面讲量化会用到。

**2. FP16 vs BF16：同样 16 位，切法不同，命运不同。** FP16 切成 1+5+10：尾数多、刻度细，但只有 5 个指数位，最大只能表示约 65504，梯度稍大就上溢成 inf，稍小就下溢成 0。早期混合精度训练要靠 loss scaling（把 loss 乘个大常数，让梯度整体平移进 FP16 的量程，更新前再除回来）打补丁。BF16 切成 1+8+7：指数位和 FP32 一样多，**量程完全相同**，代价是刻度只有 7 位尾数。实践证明这笔交换极其划算：深度学习对"刻度粗"容忍度很高（梯度本来就是 mini-batch 随机采样出来的，自带噪声），对"量程小"容忍度极低（一个 inf 就能毁掉整次训练）。所以现代大模型训练标配 BF16。FP8 更极端，且分两种：E4M3（3 位尾数，精度优先，用于前向的权重和激活）和 E5M2（5 位指数，量程优先，用于动态范围更大的梯度）——连"怎么切"都按用途定制。

**3. 整数量化与 outlier：均匀刻度的软肋。** INT8 只是 -128~127 的均匀格点，没有指数位，**自己没有动态范围**，必须外挂一个缩放因子 scale：x ≈ s·q，最简单地取 s = max|x|/127。问题来了：只要向量里有一个异常大的值（outlier），s 就被它撑大，其余正常大小的值全被压缩到少数几个格点上，四舍五入后损失惨重——**一颗老鼠屎污染的是全锅粥的精度**。而 LLM 的激活里恰好存在少数数值巨大的通道（与第1课见过的 attention sink 是同族现象），这是 LLM 量化最核心的难题。缓解思路包括更细粒度的 scale（每通道、每组各配一个），以及用旋转变换把 outlier "摊平"到各维度——今天列表里的 LightRot、GyRot 两篇做的就是后者，你已经能看懂它们的动机了。

**4. 为什么低精度=快？两条路。** 第一条走带宽：第13课说过 decode 每步时间 ≈ 权重字节数 ÷ 显存带宽，FP16 换 FP8 权重减半，decode 几乎快一倍——**哪怕计算本身仍在高精度做**。第二条走算力：Tensor Core 对越窄的类型吞吐越高，A100 上 FP16 是 312 TFLOPS，INT8 翻倍到 624 TOPS。

**5. 张量布局与 kernel。** 显存是一维的字节序列，二维张量按行优先（row-major）摊平存放；stride 记录"沿某个维度走一步要跳几个元素"。转置不搬数据、只改 stride，代价是内存不再连续（non-contiguous）。GPU 极度偏爱连续访问：相邻线程读相邻地址时，硬件能把请求合并成一次宽事务（coalescing），乱序访问则要多次搬运。kernel 就是在 GPU 上执行的一个函数（比如"逐元素加法"）；每个 kernel 都要从 HBM 读输入、把输出写回 HBM。于是连续做三个小操作 = 三次 HBM 往返；把它们**融合（fusion）成一个 kernel** = 读一次、算三步、写一次。用 roofline 的语言说：fusion 靠减少字节搬运抬高算术强度，把 memory-bound 的操作往拐点推。torch.compile 的自动融合、大名鼎鼎的 FlashAttention，核心都是这一招。

**回到论文**

有了这些概念，MixFrag 一句话就能说清：对 ViT 全模型统一用一种位宽是浪费——各组件对量化的敏感度天差地别（有些层的激活分布很"温顺"，4 bit 足够；有些含 outlier 或分布尖锐，必须 8 bit）。它分两步：（1）**测脆弱度**：每次只量化一个组件、其余保持全精度，用 KL 散度（交叉熵的近亲，度量两个概率分布的差异）比较量化前后模型输出分布变了多少，变化越大说明该组件越脆弱；（2）**分配预算**：在总比特预算约束下，把"每个组件从 {4,6,8} bit 里选一档"建模成多选背包问题求解，脆弱的组件多给比特。整个框架印证了本课的中心思想：**精度不是全局常数，而是和显存、带宽一样需要按敏感度分配的资源。**

**动手/思考**

1）跑一跑，亲眼看三个现象：

```python
import torch
# 量程：FP16 上溢，BF16 安然无恙
print(torch.tensor(70000., dtype=torch.float16))   # inf
print(torch.tensor(70000., dtype=torch.bfloat16))  # 69632（刻度粗但没爆）
# 刻度：BF16 在 1.0 附近的间隙约 0.008
print(torch.tensor(1.001, dtype=torch.bfloat16))   # 变回 1.0

# outlier 毁掉 INT8 量化
def q(x):
    s = x.abs().max() / 127
    return (x / s).round().clamp(-127, 127) * s
x = torch.randn(1000)
print((x - q(x)).abs().mean())            # 正常误差
x[0] = 100.0                              # 塞入一个 outlier
print((x[1:] - q(x)[1:]).abs().mean())    # 其余 999 个数的误差被放大几十倍
```

2）思考题：某推理引擎把权重存成 FP8，但矩阵乘仍在 FP16 下计算（读入时先反量化），decode 速度依然接近翻倍。用第13课的 roofline 解释为什么"计算没变快，整体却快了"；再想想同样的改动对 prefill 阶段收益为什么小得多。
